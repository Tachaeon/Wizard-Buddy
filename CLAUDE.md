# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Wizard-Buddy is a PowerShell Windows Forms application that places an animated GIF companion in the system tray and optionally on the desktop. The right-click tray menu exposes admin utilities, one-click winget installs, registry tweaks, and buddy-swapping. The entire application is self-contained — all GIF and icon assets are Base64-encoded and embedded directly in the script, requiring no external files at runtime.

## Running

```powershell
# Requires PowerShell 7+
pwsh Start-WizardBuddy.ps1

# Or as designed (via VBScript launcher, hidden window):
# CreateObject("Wscript.Shell").Run "powershell ... irm <url> | iex", 0, False
```

## Architecture (`Start-WizardBuddy.ps1`)

### Embedded types
Every C# type lives in **one** `$NativeSource` here-string near the top, compiled once and cached as a DLL (see v3.8.1; the in-process `Add-Type -TypeDefinition $NativeSource` is only the fallback) (Windows PowerShell runs csc.exe once per `Add-Type`, ~0.2 s each, so add new P/Invoke types to that block rather than a new `Add-Type`). It is guarded by `'Win32WB.ConsoleWB' -as [type]`, so re-running the script in the same session skips it:
- **`User32`** — P/Invoke into `user32.dll` for `ReleaseCapture` and `SendMessage`, used to implement borderless-form dragging via the `WM_NCLBUTTONDOWN`/`HTCAPTION` trick on `PictureBox.MouseDown`
- **`ShellContextMenu`** — P/Invoke into `shell32.dll` and `user32.dll` for native Windows right-click context menus (`IShellFolder`, `IContextMenu`, `TrackPopupMenuEx`). Triggered when right-clicking an application submenu item.
- **`Win32WB.*`** — `DwmApiWB` (rounded corners), `UserWB` (`EnableWindow`), `TopMostWB` (`SetWindowPos`), `IconWB` (`DestroyIcon`), `ConsoleWB` (`ShowWindowAsync`, hides the console at startup), `MemoryWB` (`EmptyWorkingSet`, see v3.8.1), `ShakeWB` (Shake to Find Pointer, see v3.9.0).

### Form and rendering
- The desktop companion is a borderless, always-on-top, taskbar-hidden `Form` with `BackColor = DimGray` and `TransparencyKey = BackColor`, making everything except the GIF transparent.
- The GIF plays in a `PictureBox` (`SizeMode = StretchImage`). Loading images via `[System.Drawing.Image]::FromStream($memoryStream)` preserves GIF animation.
- MouseWheel resizes the form; Ctrl+MouseWheel adjusts opacity.
- Dragging is implemented by calling `User32.SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)` on `PictureBox.MouseDown`, which tricks Windows into treating the click as a title-bar drag.

### Asset embedding
All buddy GIFs and menu icons are stored as Base64 strings in the script body. `Get-IconFromBase64` decodes them to `System.Drawing.Image`. To add a new buddy or icon, convert the file to Base64 and add the string as a variable.
- **Menu icons go through `Get-MenuImage`** (used by `Add-MenuItem` / `Add-SubMenuItem`), which caches each decoded image in `$MenuImageCache` (keyed by the Base64 text, or `file:<path>` for `ExtractAssociatedIcon`). Cached images are shared between menu builds, so **never dispose a menu item's `.Image`**; disposing the menu itself leaves item images alone (checked in 5.1 and 7).
- **Buddy pictures and the tray icon must stay uncached** (`Get-IconFromBase64` directly): the PictureBox animates its image and `Set-TrayIcon` disposes its copy. Swap the buddy picture with `Set-BuddyPicture`, which disposes the old one.

### Tray and menus
- `NotifyIcon` (`$Systray_Tool_Icon`) lives in the system tray with a `ContextMenuStrip`.
- Left-click shows/positions the desktop form; right-click opens the menu.
- Menu items are built with `Add-MenuItem` (top-level, Base64 icon) and `Add-SubMenuItem` (nested; supports Base64 icon or auto-extracted icon from a `.exe` path via `ExtractAssociatedIcon`).
- When `Add-SubMenuItem` receives a `-FilePath`, it stores the path in the item's `.Tag` and wires up `Add-ShellContextMenuHandler`, so right-clicking the menu item triggers the native Windows shell context menu for that executable.
- Shift+Click on application items triggers `Add-ShiftClickHandler`, which runs the target with `-Verb RunAs`.

### Key functions

| Function | Purpose |
|----------|---------|
| `Toast` | Shows a Windows toast notification using `Windows.UI.Notifications` WinRT APIs. The hero GIF is downloaded once to `%TEMP%\WizardBuddy\ToastHero.gif` and the app ID registered once per session (`$script:ToastAppRegistered`); PowerShell 7 can't load WinRT that way, so it falls back to `Show-TrayNotice` |
| `Install-Application` | Calls `winget install` silently; calls `WingetCheck` first. The winget Installs items share one handler (`$InstallWingetApp`) that reads `WingetId` / `PostInstallPath` from the item's `.Tag` |
| `Install-WindowsCapability` | RSAT installs (Active Directory, Group Policy, RSAT Tools): an elevated console running `Add-WindowsCapability`, waited on in the background; `-InstalledPath` tells success from failure |
| `WingetCheck` | Bootstraps winget by downloading the MSIX bundle if `winget.exe` is missing |
| `ClickPaste` | Downloads, extracts, and launches ClickPaste; attempts to pin it to the system tray via registry |
| `Get-ImageFromURL` | Downloads an image (GIFs included) from a URL into an `Image`; `$null` plus a message box on failure |
| `Set-FormBottomRight` | Positions the form in the bottom-right corner of a given screen's working area |

### Drag-and-drop
The form has `AllowDrop = $true`. `DragEnter` sets the effect to `Copy`. `DragDrop` accepts either a file path (`.gif` only) or a URL string, and replaces the current buddy GIF. URLs (jpg/jpeg/png/gif) go through `Get-ImageFromURL`; file paths load directly from disk. Both swap in through `Set-BuddyPicture`.

### `#region` structure
The script body is organized into regions: `Functions` → base64 icon variables → tray setup → `Buddies` → `Applications` → `Customize Windows` → `Installs` → `Scripts` → `Handlers` (drag-drop, tray events) → `Application.Run`.

### v3.3.0 (2026-09-30)
- The computer-name item is now the first entry in the buddy menu, followed by a separator.
- **Tool windows are modeless.** Speed Test, Password Generator, Scroll Jiggler and SimpleHelp Spy Detection open through `Show-ToolWindow` (`Window.Show()`) instead of `ShowDialog()`, so the buddy menu stays usable. Because their handlers now run after the `Show-*` function has returned, they can no longer see its locals by dynamic scoping:
  - `Show-ToolWindow` stores the `$UI` table in `Window.Tag`; timers keep it in `DispatcherTimer.Tag`. Every handler starts with `$UI = Get-ToolUI $this`. Per-window state (`$UI.Timer`, `$UI.Jiggles`, `$UI.LogPath`) lives in `$UI`, not in function locals. Don't use `.GetNewClosure()` instead: the closure's module scope can't see the script-scope functions when the app is run with `-File`.
  - `$ToolWindows` (script scope) maps tool name → open window. `Resume-ToolWindow` at the top of each `Show-*` brings an open instance to the front instead of opening a second; the window unregisters itself on `Closed`.
  - `Show-ToolWindow` calls `ElementHost.EnableModelessKeyboardInterop`, without which a modeless WPF window under the WinForms message loop receives no keystrokes.
  - The buddy is still shown with `ShowDialog()`, and a WinForms modal loop disables **every** window on the thread (verified), including tool windows opened before the buddy was reopened. The buddy's `Shown` handler calls `Enable-ToolWindows` (`Win32WB.UserWB.EnableWindow`) to undo that.
- Other UI-thread waits moved off the thread: `Install-Application` waits on the winget window through `Start-BackgroundTask` and launches `-PostInstallPath` in `OnComplete` (only if it exists); the PuTTY application item now calls `Install-Application` (its winget window no longer uses `-NoExit`); Group Policy Update runs `gpupdate` as a background task; Ping Google no longer passes `-Wait`; the Sandbox Proxy clipboard watch is a 1-second WinForms `Timer` that gives up after 10 minutes instead of a busy `while ($true)` loop.
- **Base64 Wizard is built in.** `Get-Base64.ps1` is gone (it only worked when `$PSScriptRoot` was set, i.e. never via `irm | iex`). `Show-Base64Wizard` is an OpsHub tool window like the others (modeless, `Resume-ToolWindow 'Base64Wizard'`): drop a file on the `DropZone` border or use Choose File to copy its Base64 to the clipboard (`ConvertTo-Base64Clipboard`, refuses folders and files over 50 MB); Decode Clipboard (`Save-Base64Clipboard`) strips an optional `data:...;base64,` prefix and writes `Downloads\Base64-<timestamp>.<ext>`, with the extension from `Get-Base64FileExtension` (leading-byte signatures, `bin` when unrecognised). Fixes carried over from the old script: EXE (`MZ`) was never detected because a 2-byte signature was compared against 4 bytes, and an unknown type silently saved nothing but still reported success.

### v3.4.0 (2026-11-04) — Android Emulator
- **Installs › Android Emulator** runs `Install-AndroidEmulator`: it writes `$AndroidEmulatorSetup` to `$env:TEMP\WizardBuddy\Setup-AndroidEmulator.ps1` and runs it in a visible `powershell.exe` console that waits for Enter. The window is waited on through `Start-BackgroundTask`; `OnComplete` offers to start the emulator.
- `$AndroidEmulatorSetup` is a **verbatim copy** of `C:\Projects\AndroidEmulator\Setup-AndroidEmulator.ps1` (outside this repo; keep them identical, ASCII-only, and no line may start with `'@`). It is per-user and pins no versions: `cmdline-tools;latest` from `https://dl.google.com/android/repository/repository2-3.xml` (re-downloaded when the index lists a newer revision), then `android sdk install platform-tools` / `emulator` (latest by default), then `android emulator create medium_phone`. No JDK: `android.exe` carries its own runtime, and its `sdk install` accepts licences itself. Gotchas found while building it:
  - Don't use `android sdk update`: it can't replace `cmdline-tools\latest`, the folder `android.exe` runs from ("Failed to extract package archive").
  - Don't use `avdmanager` either: it can't read the `devices.xml` in API 36+ images, yet still exits 0.
  - The CLI's profiles pin their own image (Android 36 for `medium_phone` as of CLI 1.1.16717390). So a newly created device is moved to the newest stable image *of the same type*, read from the `image.sysdir.1` folder (`tag.id` says `google_apis_playstore` even for tablets), by rewriting `image.sysdir.1` + `target` in the AVD's `config.ini` and `.ini`. Versions look like `36` or `37.0`; `-ext`/`-beta` builds are excluded, and `ps16k` is a separate type. Existing devices are never moved.
  - Google Play images that no AVD's `config.ini` references are removed afterwards. That step only warns on failure, because `sdk remove` contacts the repository and can fail transiently.
  - While `emulator`/`qemu-system-*` is running, the script skips the `platform-tools`/`emulator` install (their files are locked) with a warning, and still creates devices. That way **Add Device** works with an emulator open.
- **Applications › Android Emulator** is built by `Add-AndroidDeviceMenuItems`: **Start <name>** (`Start-AndroidEmulator` → `emulator.exe -avd <name>`, hidden console), a separator, then **RAM (x GB)**, **CPU Cores (n)** and **Screen (preset)** submenus. With one AVD these sit directly under the item; with several, each AVD gets a submenu. Then `Add-AndroidAddDeviceMenu` adds **Add Device**, listing the `$AndroidDeviceProfiles` (small_phone / medium_phone / medium_tablet / medium_desktop) that don't exist yet; a click calls `Install-AndroidEmulator -DeviceProfile <profile>`. With no AVD at all, clicking the item offers the install. Each choice's `.Tag` hashtable carries a `Settings` map of `config.ini` keys; one shared click handler writes them via `Set-AndroidDeviceSetting`, moves the check and relabels the parent. `Get-AndroidAvdConfigPath` resolves the file through the `path=` line in `<name>.ini`.
  - **Screen** presets (`$AndroidScreenPresets`) come from Google's device catalog in `cmdline-tools\latest\lib\sdklib.core.jar` (`com/android/sdklib/devices/devices.xml` + `nexus.xml`; xhdpi = 320, xxhdpi = 480). They write `hw.lcd.width` / `hw.lcd.height` / `hw.lcd.density`, plus `hw.initialOrientation` (landscape when width > height). The current preset is matched on width + height. Verified: the phone AVD booted with the Pixel Tablet preset reports `wm size` 2560x1600 / density 320. This changes only the screen, not the image type, so a real tablet needs Add Device › Tablet (tablet image).
  - User-facing text never shows the raw AVD name: `Get-AndroidDeviceDisplayName` title-cases it (`medium_phone` → "Medium Phone"). This applies to Start items, per-device submenus, tray notices and the install prompt. `.Tag` values and `-Name` arguments keep the raw name.
  - `Install-AndroidEmulator` takes `-DeviceProfile` (default `medium_phone`) and passes it through `Context`, so `OnComplete` offers to start that device. Install, update and Add Device share the background-task name, so a second one gets "Already running". RAM choices are capped at half the host's memory (`$script:HostMemoryMB`, looked up once) and cores at `ProcessorCount`; the device's current value is always listed. The setting takes effect at the next start. Verified: changing either one with a saved quick-boot snapshot just makes the emulator cold boot, with the new RAM and core count. They have no icon, because `$SettingsIcon` isn't defined until the later Customize Windows block. `Get-AndroidVirtualDevices` reads `*.ini` names from `ANDROID_AVD_HOME` or `~\.android\avd`, so building the menu spawns no process. **It returns a bare string for a single device**, so index it as `@(Get-AndroidVirtualDevices)[0]`; without the `@()`, `[0]` gives the first character. `Test-AndroidEmulator` offers the install when `emulator.exe` or any AVD is missing.
- `$AndroidIcon` is the emulator.exe icon, resized to 24 px.

### v3.5.1 (2026-11-04) — admin retry for Customize Windows
- The per-setting apply/undo logic moved out of `Set-RegistryAndRestartExplorer` into `Set-RegistrySetting` (throws on failure). When settings fail and Wizard Buddy isn't elevated, the warning now asks "Try these again as administrator?" and passes only the failed settings to `Invoke-ElevatedRegistry`.
- `Invoke-ElevatedRegistry` rewrites `HKCU:` (in `Path` and `UndoPath`) to `Registry::HKEY_USERS\<current SID>`, so a UAC prompt answered with a separate admin account still writes this user's hive. It builds a script from a single-quoted template, with `__FUNCTION__` (the text of `Set-RegistrySetting`), `__JSON__`, `__UNDO__` and `__RESULT__` placeholders; settings travel as JSON and are turned back into hashtables there. It runs that script through `powershell.exe -EncodedCommand` with `-Verb RunAs`, hidden. The UAC prompt is on the UI thread, where 1223 (dismissed) is swallowed. The wait runs as a background task (`<Title> (administrator)`), and failures come back through `$env:TEMP\WizardBuddy\ElevatedRegistry.txt`. `OnComplete` restarts Explorer. **`Set-RegistrySetting` must stay self-contained**, because only its own text is copied into the elevated script. Tested un-elevated under PS 5.1 and 7: an HKCU apply and undo through the HKEY_USERS rewrite, and an HKLM failure reported back.
- Which tweaks need admin: `HKLM:` (Remove Shortcut Arrows, Hide Widgets) and `HKCU:\Software\Policies` (No Bing in Start Search; standard users only have read access there by design).
- **Hide Widgets** now sets the "Allow widgets" policy (`HKLM:\SOFTWARE\Policies\Microsoft\Dsh\AllowNewsAndInterests = 0`) instead of `Advanced\TaskbarDa`. On newer Windows 11 builds, UCPD refuses `TaskbarDa` writes from PowerShell even when elevated ("Attempted to perform an unauthorized operation"). The policy turns Widgets off entirely, so the row is still `ExcludeFromAll`.

### v3.8.0 (2026-11-06) - SimpleHelp Spy Detection always on, penguin alert
- **The watcher starts with the app** (`Start-SpyWatch` right after the tray icon is shown). - **What counts as a hit:** a **new** `Remote Access Session` process (`Remote Access Session.exe`). SimpleHelp starts one in the user's desktop session when a technician connects, but one can linger after the session ends. So `Start-SpyWatch` (at launch and on the window's Start) records the PIDs already running in `$script:SpyKnownPids` (`HashSet[int]`) and ignores them. `Invoke-SpyCheck` drops PIDs that have exited (`RemoveWhere`), so a reused PID still counts as new. Any PID not in the set is a hit, and is then added to the set: one chime, log line and balloon per new process, not one every tick. The catch: a session that is already running when Wizard Buddy starts is never reported. Tested in 5.1 and 7 with a copy of `PING.EXE` renamed to `Remote Access Session.exe`. A process started before launch logged nothing over two ticks. A new process logged exactly once. A second new process logged again. The old rule, "more than two `Remote Access` processes", missed single sessions: `Remote Access.exe` is the always-running service (session 0, started at boot), and only one instance was running on James's PC, so one connection never got past 2. Verified 2026-11-06: one `Remote Access` since boot, plus a `Remote Access Session` created mid-afternoon during a connection.
- A hit chimes (`Ring05.wav`, one cached `SoundPlayer`) and appends `(Get-Date).ToString('F')` plus `(PID n)` to `$SpyLogPath` (`$env:TEMP\Logix.txt`) with `Add-Content -Encoding UTF8`. The old `Out-File -Append` wrote UTF-16 in Windows PowerShell and UTF-8 in 7, so a log shared by both editions had mixed encodings.
- **Penguin alert**: the first hit calls `Set-SpyAlert $true`. That sets `$script:SpyAlert`, switches the tray icon (`Set-TrayIcon`) and, when the buddy is on screen, its picture (through `$script:BuddyPictureBox`, set when the buddy form is built and cleared after `ShowDialog`) to `$SpyAlertBase64` (`C:\Install\pengu-pudgy.gif`, 200x200, 63 frames; defined after `$YinYangIconBase64`, **not** in `$buddyMap`). Task Manager's Memory column is the private *working set*, so it shows the lower figure.

### v3.9.0 (2026-11-09) - Shake to Find Pointer
macOS-style: shake the mouse and the pointer grows for a moment. Tray right-click toggle (after Animate Tray Icon), **on by default**: saved as `ShakeToFind` (`True`/`False`) in `HKCU:\Software\WizardBuddy`, and anything except an explicit `False` counts as on (`Test-ShakeToFind`). The check reads `[Win32WB.ShakeWB]::IsRunning`. There is a `$HelpSections` row too.
- **Everything runs in C#** (`Win32WB.ShakeWB` in `$NativeSource`): `Start()` launches a background thread, `Stop()` joins it, `Restore()` = `SystemParametersInfo(SPI_SETCURSORS)`. No PowerShell runs on the mouse path, and no WinForms reference is needed (`Add-Type -ReferencedAssemblies` breaks under pwsh 7). The thread body is wrapped in `try/catch`, because an unhandled exception on that thread would kill the whole app. Its `finally` restores the cursors and frees the cached handles.
- **Detection** (the PowerToys Find My Mouse idea, `FindMyMouse.cpp`): the thread calls `GetCursorPos` every 15 ms while the mouse moves and every 50 ms while it's still, and keeps the last 600 ms of positions. It counts as a shake when the path travelled is >= 1000 px x (`GetDpiForSystem()` / 96) **and** >= 4x the diagonal of the box the positions stayed in, i.e. it went back and forth. PowerToys uses raw input and a "distance / diagonal" factor too; ShakeIt's "one 70 px move inside 150 ms" rule fires on ordinary flicks. A held left/right button clears the history: that's dragging or selecting, and shaking a window by its title bar is Windows' own Aero Shake. It doesn't start while `SHQueryUserNotificationState` reports a full-screen app (2), D3D full-screen (3) or presentation mode (4).
- **Enlarging**: 5 steps, 30 ms apart, from the user's base size up to 4x it (capped at 256). Each step calls `LoadImage(file, IMAGE_CURSOR, size, size, LR_LOADFROMFILE)`, then `SetSystemCursor(CopyIcon(h), id)` for Arrow (32512), IBeam (32513) and Hand (32649). SetSystemCursor owns and destroys the handle it is given, so the loaded handle is cached per path+size and only copies are passed. When the shake stops, it holds for 500 ms, steps down, and at level 0 calls `Restore()`, which reloads the user's real scheme, size and color from the registry.
  - Paths come from `HKCU\Control Panel\Cursors` (`RegGetValueW` with `RRF_RT_REG_SZ`, which also returns `REG_EXPAND_SZ` values, already expanded). Empty values fall back to `%windir%\Cursors\aero_arrow.cur` / `aero_link.cur`; there is no aero I-beam file, so the I-beam is skipped then. They are re-read at the start of every shake, and the cache is dropped if they changed.
  - **The base size is `CursorBaseSize`, not `SM_CXCURSOR`.** On James's PC, Settings › Accessibility › Mouse pointer size writes `CursorBaseSize = 48` and generated `%LOCALAPPDATA%\Microsoft\Windows\Cursors\*_eoa.cur` files, yet `GetSystemMetrics(SM_CXCURSOR)` still says 32, and so does `GetIconInfo` on the system arrow. `SM_CXCURSOR` is only the fallback.
  - The Microsoft Q&A answer "SetSystemCursor ignores the size, only SM_CXCURSOR is used" does **not** hold for cursors loaded from file. Measured: requests for 64/96/128/192 gave exactly those sizes. A step costs 14-34 ms and the restore 56 ms.
- **Restore safety**: startup always calls `Restore()` first. A killed process leaves the system cursor big until sign-out, and this undoes that on the next start. Exit calls `ShakeWB::Stop()` before `Stop-Process`, which skips every cleanup.
- **Tested** in 5.1 and 7 (scratch scripts drove `SetCursorPos`, and the arrow size was read with `GetIconInfo`): a slow straight move stays at 32; a 300 px sine shake reaches 192; it's back to 32 about 1.2 s after; `Stop()` while big restores at once; a fast flick across the screen and back stays at 32. Cost: ~30 M thread cycles per 5 s at the 15 ms poll (~0.2-0.3% of one core). Process-level CPU measurements were below the noise. **Don't judge it by `TotalProcessorTime`**: it is sampled per clock tick, and a thread that wakes every tick gets charged whole ticks, so 94 to 484 ms per 5 s showed up for identical loops. Use `QueryThreadCycleTime`.
- Not handled: only Arrow, IBeam and Hand grow (wait, resize and other cursors don't). A cursor scheme change during a shake is picked up at the next shake.

### v3.9.3 (2026-11-09) - Smooth shrink
James reported the shrink as jittery. Three causes, three fixes:
- **Big steps**: 5 levels from 48 to 384 is ~67 px a jump. Now `Levels = 16` (~21 px); growing still takes 4 steps (`GrowLevelsPerStep = 4`), shrinking goes one level per `ShrinkStepMs = 30` (~0.5 s in total, after the 700 ms hold).
- **Swap cost grows with area**: `SetSystemCursor` for all three cursors measured ~5 ms at 64 px, ~15 ms at 128, ~47 ms at 256, ~100 ms at 384, so every step near full size ran late. `Apply` now resizes only the cursor on screen (`VisibleCursor()`: `GetCursorInfo().hCursor` compared with `LoadCursor(NULL, OCR_*)`). `applied[]` remembers each cursor's current size, and `Apply(level)` runs on every pass while `level > 0`, so a cursor that appears mid-shake (arrow -> I-beam over text) is resized within ~15 ms. At level 0, `Restore()` resets all three.
- **Uneven timing**: the shrink level is now computed from the clock (`Levels - (sinceShake - HoldMs) / ShrinkStepMs`), so a slow step is made up on the next one instead of stretching the animation. In-between sizes are loaded by `Preload()` (one level per pass) while the pointer is at full size, so the shrink doesn't wait on `LoadImage`. Failed loads are cached as `IntPtr.Zero` (not retried), and `ClearCache` skips them.
- *(Levels, `Preload()` and the cursor cache were replaced in v3.9.4, below.)*
- Testing caveat: a second Wizard Buddy instance reacts to the same synthetic shake and calls `SPI_SETCURSORS`, which makes `applied[]` stale and ruins timings. Close other instances before measuring. Read the size of the *visible* cursor (`GetCursorInfo`), not `LoadCursor(32512)`.

### v3.9.4 (2026-11-09) - Frame-by-frame shrink
James said v3.9.3 was still jittery. Measured with no other instance running, it updated only every 31-63 ms and skipped levels near the top. Two limits: `Thread.Sleep` rounds up to 15.6 ms timer ticks, and one 384 px `SetSystemCursor` costs ~34 ms (~4 ms at 128, ~15 at 256: about 0.23 us per pixel). `CopyIcon`+set, `LR_CREATEDIBSECTION` and a fresh `LoadImage`+set all measured the same, so the swap can't be made cheaper.
- **No levels.** `grown` (0..1) follows a `Stopwatch` (`TickCount` is 15.6 ms granular). Shaking raises it linearly over `GrowMs = 150`. After `HoldMs = 700`, it falls over `ShrinkMs = 600` as `peak * (1 - u^2)`, easing in: slow at large sizes, where frames are expensive, faster at small ones, where they're cheap. That keeps the per-frame jump small. `SizeFor(grown)` rounds to `SizeStep = 2` px, and `Apply(size)` skips unchanged sizes, so it's safe to call on every pass while big.
- **No cache.** `Apply` calls `LoadImage` from the file each frame and hands the handle straight to `SetSystemCursor`, which owns it (it's destroyed only if the set fails). `Preload`, `GetCursor`, `ClearCache` and `CopyIcon` are gone. Still only the visible cursor is resized (`VisibleCursor()` / `applied[]`).
- **1 ms timer only while animating.** `SetFineTimer` calls `timeBeginPeriod(1)` while growing or shrinking (`FramePollMs = 4`) and `timeEndPeriod(1)` otherwise and in `finally`. That's about 1 s per shake; never leave it on.
- Measured in 5.1 and 7: 21-23 frames over ~530 ms. Frames are 8-15 ms apart at small sizes and 40-60 ms at the top (the probe's `GetIconInfo` on a 384 px cursor adds to that). Max jump 22-28 px; v3.9.3 jumped 42-67 px. A lower `MaxSize` is the only way to faster top frames (256 px roughly halves the cost).
